## P0

### BUG-51 · Render failure with unsaved work: window can't be closed, session orphaned

- **Where:** `apps/front/src/main.tsx` (`<ErrorBoundary><App/></ErrorBoundary>`),
  `apps/front/src/components/ErrorBoundary.tsx`, `apps/back/src/main.ts` `close` handler
  (~83-87).
- **What:** when the boundary trips, `App` unmounts and with it the
  `onCloseRequested` listener registered by `useDocumentCore`. `main.ts` calls
  `event.preventDefault()` on **every** `close` and waits for the renderer to answer
  through `confirmWindowClose`, so the X button / Alt+F4 do nothing and the process has
  to be killed. The boundary's "Recargar" runs `window.location.reload()`: the front
  forgets the session while the backend keeps it dirty, with its watcher, and nothing
  can re-attach to it. No `render-process-gone` / `unresponsive` handler exists.
  The open `Maximum update depth exceeded` bug (nested Tablix drag) reaches this path.
- **Repro (not run):** open a report, edit (dirty), force a render error (e.g. throw from
  a child); click the window X.
- **Expected:** the window can always be closed, with an explicit choice about unsaved
  work; reloading the UI re-attaches to live sessions; the boundary says the changes are
  still in memory.
- **Fix (proposed):** close timeout in main with a native `dialog.showMessageBox`
  ("Cerrar sin guardar / Cancelar"); handlers for `render-process-gone` and
  `unresponsive`; a `listSessions` channel so the renderer can re-adopt sessions after a
  reload (same mechanism the tabs phase A needs).
- **Status:** fixed. Close watchdog in main (2 s → native «Cerrar sin guardar / Cancelar»),
  renderer acknowledgement (`acknowledgeCloseRequest`), `render-process-gone` (reload or
  close) and `unresponsive` handlers, and `listSessions` + re-adoption of live sessions on
  mount; the boundary copy now says the work stays in memory. Covered by: unit
  `session.service.resilience.spec.ts` (`listSessions`) and E2E `resilience.spec.ts`
  (UI reload → «Sesión recuperada»), and unit `windowLifecycle.spec.ts` (watchdog,
  `render-process-gone`, `unresponsive`). Only the Electron `dialog` wiring in `main.ts`
  has no automated test.

### BUG-52 · Save-time conflict isn't surfaced and "overwrite" can't succeed

- **Where:** `SessionService.ts` `save` → `referenceStillOnDisk` (~163-185, ~486-510);
  `apps/front/src/hooks/useDocumentCore.ts` `save`.
- **What:** when the watcher missed an external change, `save` returns `E_CONFLICT`.
  The front only calls `setError(...)`: a banner that disappears after 6 s, with no
  conflict dialog (there is no `E_CONFLICT` handling in the front). If the user reaches
  the dialog some other way, "Guardar y sobrescribir" calls `save` again and fails
  again, because on this path the backend does **not** advance the disk reference
  (`onExternalChange` does). With the "close with unsaved changes" guard the dialog stays
  open with no visible reason.
- **Expected:** a rejected save opens the conflict dialog; "overwrite" then succeeds once;
  a **different** later external change is still detected.
- **Fix (proposed):** front: `E_CONFLICT` → `setConflict(doc.path)`. Back: when rejecting
  for a conflict, set `lastWriteMs/Size` to what is on disk (as `onExternalChange` does).
- **Status:** fixed. On a conflict rejection the backend advances `lastWriteMs/Size` to the
  current disk state (a later «overwrite» succeeds once; a different later change is still
  detected) and the front maps `E_CONFLICT` to `setConflict(doc.path)` with a persistent
  banner. Covered by: unit «conflicto al guardar» (advance + later detection). The front
  trigger (E_CONFLICT → dialog) has no E2E: the race window is hard to force.

## P1

### BUG-53 · Stale conflict after an external reload / unreadable file

- **Where:** `SessionService.ts` `onExternalChange` (final `catch`, ~440-443);
  `useDocumentCore.ts` `onDocumentChanged` handler.
- **What:** the final `catch` emits `conflictDetected` even when the session is **not**
  dirty (a file half-written by Report Builder or git fails to parse). When the file is
  complete the watcher fires again and the backend reloads silently
  (`documentChanged`, `reason: 'external'`), but the front never clears `conflict`.
  The banner and dialog stay, and "Guardar y sobrescribir" would overwrite a good file.
- **Expected:** `conflict` is cleared on an external reload; an unreadable file with no
  local edits produces a soft notice, not a conflict.
- **Status:** fixed. A clean session with an unreloadable external change emits
  `externalReloadFailed` (`unreadable`/`unsupportedSchema`) as a soft status notice, and a
  successful external reload clears `conflict`. Covered by: unit (clean + corrupt → soft
  event; valid again → external reload) and E2E «aviso suave» (`resilience.spec.ts`).

### BUG-54 · Double Open leaks a session; no busy state; double Save may false-conflict

- **Where:** `useDocumentCore.ts` `openPath` (~306-328), `createNew`;
  `SessionService.ts` `save` / `referenceStillOnDisk` / `writeTo`.
- **What:** (a) Open, New and Save have no in-progress state and no disabled controls.
  Two quick opens (double click on a recent, two dropped files) both capture the same
  stale `doc` closure; each `setDoc` replaces the previous session without closing it, so
  one session and its watcher leak. (b) **Not reproduced:** a second Save issued between
  the `rename` of the first and the update of `lastWriteMs/Size` sees a different mtime
  and bytes different from `originalBytes` and reports a false `E_CONFLICT`. The window
  is narrow; `NodeFileSystemAdapter` documents double Ctrl+S as a real case.
- **Expected:** one file operation at a time; "Abriendo… / Guardando…" after ~300 ms.
- **Fix (proposed):** `busy` flag in the hook; per-session mutex in `SessionService` for
  `save` / `saveAs` / `reload`.
- **Status:** fixed. A per-session queue in `SessionService` serializes
  `save`/`saveAs`/`reload` (a double Ctrl+S cannot false-conflict) and a synchronous `busy`
  guard in the front disables the Fichero group and shows «Abriendo…/Guardando…» after
  300 ms. Covered by: unit (instrumented interleaving) + E2E regression; the double click
  itself has no deterministic E2E.

### BUG-55 · File deleted or moved externally goes unnoticed

- **Where:** `ChokidarWatcherAdapter.ts` (only `change` and `add`);
  `SessionService.ts` `referenceStillOnDisk` (returns `true` when `stat` fails).
- **What:** if the file disappears the editor keeps working as if nothing happened and
  the next Save recreates it silently.
- **Expected:** an amber notice ("El fichero ya no existe en disco. Guardar lo recreará,
  o usa Guardar como…").
- **Fix (proposed):** subscribe to `unlink` and emit an event; handle it in the front.
- **Status:** fixed. The watcher subscribes to `unlink` (ignores `writing` and rename-over
  via `stat`); the backend emits `fileMissingChanged` on transitions and the front shows an
  amber banner that clears when the file returns or on save. Covered by: unit (transitions)
  and E2E «fichero desaparecido» (`resilience.spec.ts`).

### BUG-56 · `saveAs` leaves the session inconsistent if the watcher throws

- **Where:** `SessionService.ts` `saveAs` (~187-209).
- **What:** after `writeTo` succeeds, `session.filePath` is switched and
  `fileWatcher.watch` is awaited **unguarded**. If it rejects, the file is written,
  `originalBytes` already points at it, but `markSaved` never runs: the session stays
  dirty, has no watcher and the exception leaves the use case (how the IPC layer maps it
  was not verified).
- **Expected:** `try/catch`; on failure, still mark saved and warn "guardado, pero no se
  vigilan cambios externos". Better: create the new watcher before dropping the old one.
- **Status:** fixed. `saveAs` creates the new watcher before dropping the old one, inside
  `try/catch`: the save still completes (session marked clean, new path) and
  `SaveResult.warning` reports that external changes are not watched (the front appends it
  to the status). Covered by: unit (`failNextWatch`).

### BUG-57 · Actionable errors auto-dismiss after 6 s

- **Where:** `useDocumentCore.ts` `setError` (`ERROR_BANNER_MS = 6000`, `hasErrorDetails`).
- **What:** only errors carrying validation details are persistent. `E_UNSUPPORTED_SCHEMA`
  (long text with instructions), `E_CONFLICT` and `E_IO` on save vanish before they can be
  followed. Compounds BUG-52. (Was item P3 #8 of `docs/ux/0002`; raised to P1.)
- **Expected:** persistent until dismissed for those codes; auto-dismiss only for
  command-level errors.
- **Status:** fixed. `setError(msg, { persistent })`; `E_UNSUPPORTED_SCHEMA`, `E_CONFLICT`
  and `E_IO` no longer auto-dismiss (`isPersistentErrorCode`, with spec); command-level
  errors stay ephemeral. No E2E (timing behaviour).

### BUG-58 · Status bar leaks internal command names and floods the live region

- **Where:** `useDocumentCore.ts` `sendCommand` (`Comando '${command.cmd}' aplicado (v…)`),
  `apps/front/src/components/StatusBar.tsx` (`role="status"`, the app's only live region).
- **What:** after every edit the status shows e.g. `Comando 'setStyle' aplicado (v12)`:
  internal names and versions with no meaning for the user. Being the only live region, a
  screen reader would announce every edit.
- **Expected:** user-language messages for notable actions; silence for routine edits.
- **Status:** fixed. Routine commands no longer write to the status bar; undo/redo lose the
  version suffix; `Recargado desde disco` without `(vN)`. Covered by: E2E «estado
  silencioso» plus two stale assertions updated (`file-lifecycle`, `rdlc-designer`).

### BUG-59 · Window/taskbar title never shows the report name or unsaved state

- **Where:** `apps/front/index.html` (static `<title>`), no `document.title` anywhere in
  `apps/front/src`; `BrowserWindow` created with a fixed title.
- **What:** the title bar and taskbar can't show the report or that it has unsaved
  changes; the `*` exists only in the footer. Worsens with several windows/tabs.
- **Expected:** `Nombre.rdlc * — RDLC Report Designer`.
- **Status:** fixed. `document.title` is `Nombre.rdlc * — RDLC Report Designer`
  (`formatWindowTitle`, with spec). Covered by: E2E title test (`resilience.spec.ts`).
